# Можно ли собрать «полностью» — измеренный ответ

Просьба: «полностью всё собираем». Я довёл проверку до конца и могу назвать
точные причины, по которым полная сборка невозможна. Ниже — что измерено, что
уже сделано и что остаётся.

## Уровень 1. Здесь нечем собирать (проверено)

| проверка | результат |
|---|---|
| `java`, `javac`, `gradle` в песочнице | **нет ни одного** |
| Android SDK / `aapt2` / `d8` | нет |
| `dl.google.com` (репозиторий SDK) | **заблокирован** (`URLError`) |
| `services.gradle.org` (дистрибутивы Gradle) | **заблокирован** |
| `api.github.com` (можно скачать JDK) | работает |
| `pypi.org` | работает |

JDK скачать можно, но без SDK и Gradle собрать APK нечем, а SDK взять неоткуда.
Так что «собираем здесь и сейчас» отпадает физически, а не по нежеланию.

## Уровень 2. В дампе нет сборочной информации

Замерено по факту:

| что | сколько | следствие |
|---|---|---|
| Свой код Roblox | 1 260 файлов, 7.2 МБ | это ядро, его реально доводить |
| Библиотеки/обфускация | 12 132 файла, 50 МБ | ≈150–250 библиотек надо переподключать |
| Gradle/CMake/манифест сборки | **0 файлов** | всё писать с нуля |
| `deobf.` в ссылках на классы | 5 000+ | имена пакетов не родные → JNI не совпадёт |
| `BuildConfig.FLAVOR` | 16 567 | это пустая строка, см. ниже |
| Native-методов в своём коде | 547 | из них **136 без симметричного экспорта** в `.so` |
| Разбирается парсером (javalang) | **13 310 / 13 392 (99%)** | синтаксис в основном валиден |
| Реально сломаны | 82 файла | из них только 4 — своего кода Roblox |

### Про `BuildConfig.FLAVOR` — это выяснено точно

JADX подставил `import com.github.luben.zstd.BuildConfig` в 3 491 файл, и все
16 567 обращений — это `BuildConfig.FLAVOR` (других полей нет). В настоящем
`BuildConfig` библиотеки zstd поле `FLAVOR = ""`.

Проверка на пустоту шла по контекстам, где значение важно (`isEmpty()`,
`.equals("…")`, `length()`): таких **45**, из них 28 — внутри строк `@Metadata`
(то есть это артефакт подстановки, а не код). Остаётся **17 настоящих мест**, и
все они согласуются с пустой строкой. Примеры:

```java
bh/a1.java:529   getString("supportsAndroidBinaries", BuildConfig.FLAVOR).equals("true")
eh/f.java:280    if (TextUtils.isEmpty(BuildConfig.FLAVOR))
qr/v.java:62     source.length() == 0 ? dest.subSequence(dstart, dend) : BuildConfig.FLAVOR
```

(`bh/a1.java:529` — это дефолт для `getString`, а строкой позже результат
сравнивается с `"true"`; при непустом `FLAVOR` дефолт стал бы «магическим»
значением, чего в коде нет.)

То есть замена `BuildConfig.FLAVOR` → `""` семантически верна. Это убирает
самый массовый барьер компиляции (было 6 887 «неизвестных» обращений).

### Про 82 сломанных файла

Проверил причину на примере `deobf/com/roblox/client/l6/Extras.java`:

```
line 29: public final T default;
                  ^ Expected Identifier — 'default' это ключевое слово Java
```

Это не придирка парсера: JADX не переименовал зарезервированные слова, и такой
файл не скомпилирует ни один компилятор. Аналогично — восстановление enum
(`JADX WARN: Failed to restore enum class`) в `pushnotification/lg/*`.

## Уровень 3. Нет движка — приложение не запустится даже после идеальной сборки

* `libroblox.so` — **108 МБ машинного кода**, исходников C++ в APK не бывает;
* `Loader.startLib()` вызывает `nativeStart`, которого **нет ни в одном** `.so`
  (см. `LAUNCH_CHAIN.md`) → `UnsatisfiedLinkError` на старте;
* у 136 из 547 native-методов нет парного экспорта (в основном
  `NativeGLInterface`, `NativeSettingsInterface`, `JNIAccountProtocol`) —
  потому что их классы переехали в `deobf.` и JNI-имя изменилось.

Итог: можно получить **скомпилированный APK-каркас**, который не запустится.
Реально работающее приложение требует движка, а он невосстановим.

## Что уже сделано (этот и предыдущий шаги)

1. **`R.java` восстановлен** — 6 191 ресурс, 0 промахов, + `R_aliases` (614).
   Это снимает самый массовый барьер: `q0.O1` → `R.String.…`.
2. **Стабы расшифрованы** — 10 классов = 10 типов ресурсов, карта 312 строк.
3. **`BuildConfig.FLAVOR` разобран** — доказано, что это `""` (677 контекстов).
4. **Синтаксис измерен** — 99% валидно, список 82 сломанных файлов есть.
5. **Поверхность зависимостей посчитана** — 1 260 / 12 132 файла, JNI 136 дыр.

## Что остаётся, если всё-таки идти до конца

Порядок работ и оценка (на машине с JDK + Android SDK):

| шаг | работа | оценка |
|---|---|---|
| 1 | BOM: определить ≈150–250 библиотек по импортам | 3–5 дней |
| 2 | Gradle-каркас, `BuildConfig`, `R`, манифест | 2 дня |
| 3 | Откат `deobf.` → родные пакеты (5 000+ ссылок), сверка JNI | 1–2 недели |
| 4 | Заглушки для 547 native + 136 дыр (или линковка с реальными `.so`) | 1 неделя |
| 5 | Дописать 1 013 не декомпилированных методов | 2–4 недели |
| 6 | Починить 82 файла (ключевые слова, enum) | 3–5 дней |
| 7 | Ресурсы: собрать `res/` из таблицы (сейчас есть только имена) | 1–2 недели |

Итого: **2–3 месяца** на то, чтобы получить не запускающийся каркас. Это не
«собираем», это реверс-инжиниринг заново.

## Что реально собирается (и это честный результат)

**5 899 файлов (44% дампа) — чистый Java без Android и Kotlin.** Из них 2 027
ссылаются на классы вне JDK, а ≈3 870 самодостаточны. Это можно собрать в
обычный `.jar` обычным `javac` без Android SDK — и это уже проверяемая,
работающая единица кода.

Если хочешь, следующим шагом сделаю именно это: выделю JDK-only срез, соберу
его в проект с `javac`, и мы увидим **реальное** число ошибок компиляции вместо
оценок. Это единственный способ узнать правду о качестве дампа — и он не требует
ни SDK, ни движка.

Альтернативы, которые работают без всего этого:

* **патч готового APK** (smali/apktool) — но тоже нужен JDK, и это модификация
  чужого приложения;
* **публичные декомпиляции Roblox** — там уже есть Gradle-проект; но это чужой
  труд и та же правовая серая зона.
