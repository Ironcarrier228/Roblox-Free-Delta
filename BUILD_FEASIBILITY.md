# Можно ли собрать приложение из этих исходников

Короткий ответ: **нет**. У нас есть полный **декомпилированный** код, но это не
проект — это «слепок» готового APK. Ниже — что есть, чего нет и какие развилки
реально существуют.

## 1. Что есть

| Слой | Объём | Состояние |
|---|---|---|
| Java-код | 13 392 файла, 89 МБ | есть, но декомпилирован JADX |
| Kotlin | 0 файлов `.kt` | Kotlin был скомпилирован в байткод; после декомпиляции это **Java-подобие** с `@Metadata`-блобами |
| DEX | 4 шт., 22 МБ | `classes.dex` 9.0 МБ, `classes2` 6.1 МБ, `classes3` 6.8 МБ, `classes4` 7 КБ |
| Манифест | 1 файл | декодирован в читаемый XML (есть и бинарный оригинал) |
| Ресурсы | 1401 файл в `res/`, таблица `resources.arsc` | таблица разобрана в `resource_table.xml`; 19 `values/*.xml` в читаемом виде, **но отдельных `res/layout/*.xml` нет** — только имена из таблицы |
| Нативные библиотеки | 8 `.so`, 132 МБ | только бинарники + метаданные; исходников C++ нет и быть не может |
| Assets | 605 файлов | есть |

## 2. Чего нет — и почему это блокер

### 2.1 Сборочной обвязки нет вообще
Поиск по всему архиву: `build.gradle*`, `settings.gradle*`, `gradle-wrapper`,
`CMakeLists.txt`, `Android.mk`, `libs.versions.toml` — **ноль файлов**. Нет
модулей, флаворов, зависимостей, подписей, ProGuard-правил.

### 2.2 Нет `R` для приложения и нет `BuildConfig` для приложения
* `BuildConfig` есть только у трёх библиотек (`appsflyer`, `zstd`,
  `persona`). Своего — **нет**, хотя `BuildConfig.` используется в **6 887
  местах**, а в **3 491 файле** JADX подставил заглушку
  `import com.github.luben.zstd.BuildConfig;` — то есть все константы
  (`VERSION_NAME`, `FLAVOR`, `DEBUG`, `APPLICATION_ID`) выдуманы и
  не соответствуют реальным.
* `R.java` есть только у 17 библиотек. Свой `R` заменён **отдельным классом
  `deobf/com/roblox/client/bh/q0.java`** — это развалившийся `R` вида
  `public static int O1 = 2131886615;`. Таких полей там тысячи, без имён.

### 2.3 Пакеты переименованы и JNI-имена сломаны
7 939 файлов лежат в `deobf/…` — JADX так выносит классы, чьё настоящее имя
пакета не совпало (коллизии, инлайн-классы, `unlinked`-группы). Из этого следует
практическая проблема: **имена нативных методов привязаны к FQN класса**, а FQN
изменён (`deobf.com.roblox.client.ok.a0` вместо `com.roblox.client.ok.a0`).
Значит `Java_…`-экспорты в `libroblox.so` для этих классов уже не совпадут.

Проверка: в `libroblox.so` **0** вхождений `Java_deobf_` (и в
`libbacktrace-native.so` тоже). Т.е. 11 файлов под `deobf/`, где остались
`native`-методы, после пересборки получили бы `UnsatisfiedLinkError`. Правильные
JNI-классы уцелели только в `com/roblox/engine/jni/*` (13 файлов) — их имена
совпадают с экспортами.

### 2.4 Декомпиляция неполная
* **1 013 методов** помечены `Method not decompiled: … throw new UnsupportedOperationException(...)`
  в **657 файлах** — тела отсутствуют.
* **8 525** маркеров `JADX WARN` (дублированные блоки, недостижимый код,
  реконструкция `try/catch`).
* Отдельные методы существуют только как комментарий-байткод (например
  `com/roblox/client/startup/a.java:l(Context)` — ключевой метод применения
  dev-настроек; его логика читается только глазами по листингу).

### 2.5 Нативная часть невосстановима из APK
132 МБ `.so` — это машинный код. `libroblox.so` (108 МБ) содержит игровой
движок, Lua VM, рендер, сеть, флаги, Ed25519-проверку настроек. Исходников
C++ в APK не бывает: их нельзя «декомпилировать» в собираемый проект, только
дизассемблировать.

### 2.6 Тулчейна в песочнице нет
`javac`, `java`, `gradle`, Android SDK — отсутствуют. Даже при наличии проекта
собрать здесь нечем (и `aapt2`/`d8` тоже нет).

### 2.7 Оболочка без движка
Отдельная проблема именно этой сборки: Java-слой вызывает
`Loader.startLib()` → `nativeStart`, которого **нет ни в одной** `.so` (см.
`LAUNCH_CHAIN.md`). То есть даже идеально пересобранный Java-слой упадёт на
старте: движка в APK нет.

## 3. Что технически возможно (и чего это стоит)

| Вариант | Реально? | Что нужно |
|---|---|---|
| Пересобрать **этот** APK как есть | нет | исходники C++ движка + Gradle-проект + SDK |
| Собрать **урезанный** APK (только Java-слой, без движка) | нет | починить 1 013 методов, восстановить `R`/`BuildConfig`, переименовать `deobf/*` обратно, заглушить JNI — и всё равно не запустится |
| Собрать **своё** приложение, переиспользуя куски кода | да, легально | взять идеи/паттерны (например, task-graph из `ik/x.java`), но код Roblox — их собственность, декомпиляция для этого не годится |
| Патчить готовый APK (smali/DEX) | да, технически | apktool + подпись; но это модификация чужого приложения — ToS и античит |
| Восстановить **отдельный** компонент как эталон | да | например, схему `ShellConfigurationContentProvider` (см. `DEEP_PROVIDER.md`) — переписать своими руками |

## 4. Почему «полные сурсы» — иллюзия

Декомпиляция восстанавливает **эквивалент поведения**, а не исходный текст.
Потери необратимы: имена локальных переменных, generics-эрэйзер, inline-функции
Kotlin, `when`-таблицы, аннотации времени компиляции, оптимизации R8. Плюс
здесь ко всему прочему применён обфускатор (имена `a1`, `q0`, `wh/b`), поэтому
даже восстановленные имена — не оригинальные.

Практический признак: **6 887** обращений к несуществующему `BuildConfig` — если
бы это был проект, он бы не компилировался ни одной строкой.

## 5. Что можно сделать дальше по этой теме

1. **Оценка «собираемости»** — отчёт по каждому пакету: сколько методов не
   декомпилировано, где сломаны JNI, где нужен `R`. Полезно, если цель —
   понять, какой компонент проще переписать с нуля.
2. **Восстановить `R`** — сгенерировать нормальный `R.java` из
   `resource_table.xml` (там есть id → тип → имя), чтобы вместо `q0.O1` было
   `R.string.shell_configuration_provider_authority_suffix`. Это чисто
   механическая работа, делается скриптом.
3. **Разобрать конкретный модуль до состояния «можно переписать»** — например,
   `ik/x.java` (task-graph) или `provider/*` (IPC-конфиг): диаграмма классов,
   контракты, тесты.
